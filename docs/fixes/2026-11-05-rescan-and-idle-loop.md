### Idle resize-observer loop in bottom-stack and three unthrottled page scans (2026-11-05)

**Why.** A CPU profile (4x slowdown, 390 px) showed `querySelector(All)` costing 475 to 1,011 ms per page, with `omega-bottom-stack.js` the top caller on three of four pages. Counting calls on an **idle** page (nothing happening, between 3 s and 8 s after load) found the cause: `omega-bottom-stack.js` created ~58 new `ResizeObserver`s a second on `journal.html` (160 to 448 in 5 s) and ~28 a second on `dashboard.html` (81 to 222), with ~170 `getComputedStyle` calls a second. `measure()` ended by calling `observeChrome()`, which disconnected the observer and built a new one; a new `ResizeObserver` reports every element it is given once, immediately, which called `schedule()`, which ran `measure()` again. A loop with no end, for as long as any page stayed open (CPU and battery on a phone). Blocking that one script took the idle count to 0. Separately, three observers ran a whole-page `querySelectorAll` on every mutation batch with no rate limit: the heading signs in `omega-content.js` (inserting a sign is itself a mutation), `holo()` in `omega-9d.js`, and the password-field scan in `bg.js`. The other two observers in that group (`omega-alive.js`, the `enhance` pass of `omega-content.js`) were already debounced and element-only, and `omega-motion.js` polls at most 12 times, so they were left alone.

**Fix.** `omega-bottom-stack.js`: one `ResizeObserver` for the life of the page; `observeChrome()` only `observe()`s newly found elements and `unobserve()`s ones that left. `omega-content.js`, `omega-9d.js` and `bg.js`: the observer callback now schedules one pass per animation frame (`requestAnimationFrame`, `setTimeout` fallback) instead of one per batch. What each pass does is unchanged.

**Verified.** Idle `journal.html`: resize observers created stay at 4 (was +288 in 5 s), `getComputedStyle` calls +2 in 5 s (was +866). Behaviour of `omega-bottom-stack.js` against the original code (`git show origin/main:`), 6 scenarios (390 and 1280 px, `journal`/`dashboard`/`gaming`; add furniture, grow it, add a transient banner, remove both): the published `--omega-chrome-bottom`, `--omega-transient-bottom` and `data-omega-transient` match in 6 of 6. Cost at 4x CPU, median of 3, all four fixes against before: `querySelector(All)` time -33%, -38%, -36%, -32% (`journal`, `dashboard`, `gaming`, `life`); page script time -13%, -14%, -8%, -8%; style-recalculation time -14%, -18%, -8%, -5%; `bottom-stack` is no longer a top caller on any of them. `node scripts/verify-runtime.js --all`: result in the PR. `scripts/tests/test_rescan_fixes.py` pins the shape.

**Not done / not verified.** The number of style recalculations did not move (101-181 per load, within 3%): they come from elsewhere (about 95 stylesheets, modules injecting `<style>`). `dashboard.html` still makes ~570 `getComputedStyle` calls in 5 idle seconds with `omega-bottom-stack.js` blocked, so another module polls there; not found yet. `bg.js` still has several observers; only the unthrottled one was changed. Measured headless on a local server; not on a real phone, so battery gain is inferred from CPU activity, not measured.
