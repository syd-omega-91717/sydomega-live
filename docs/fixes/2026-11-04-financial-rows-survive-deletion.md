### Financial rows survive account deletion (D1) and erasure contract reads migrations (2026-11-04)

**Why.** Decision D1 says financial records are anonymised on account deletion, never deleted. Replaying every migration on a local replica and reading the real foreign keys showed three tables did the opposite: `commission_contracts` (`user_id` nullable, FK to `auth.users` ON DELETE CASCADE), `sovereign_points_ledger` (NOT NULL, CASCADE) and `omega_service_orders` (NOT NULL, RESTRICT, so a member with an order could not be deleted at all). Separately, `scripts/erasure-policy-contract.py` read only `supabase/live-schema.json` (captured 2026-10-06) and so missed 6 member-data tables created later by migrations.

**Fix.** `20261104090000_financial_rows_survive_account_deletion.sql`: finds the single-column `user_id` foreign keys to `auth.users`/`public.profiles` in the catalogue, drops them by whatever name they carry, drops NOT NULL, and re-adds the key as ON DELETE SET NULL. Reads and writes no row. Registered in `supabase/pending-migrations.json` (PENDING_REVIEW / NOT_APPLIED). The contract now also parses `supabase/migrations/*.sql` (`--migrations`), and `config/erasure-policy.json` classifies the 6 tables it found (167 rows, all `reviewed:false`; two `pending_decision`).

**Verified.** On a PostgreSQL 16 replica built by replaying 414 migrations: after the migration the three FKs have `confdeltype = 'n'` and `user_id` is nullable; inside a transaction (rolled back), deleting an auth user left one row in each table with `user_id` NULL, including an order that previously blocked deletion. `python3 -m unittest scripts/tests/test_erasure_policy_contract.py`: 17 pass.

**Not done / not verified.** Not applied to production, whose real keys are unknown until `docs/runtime/production-facts.sql` is run. The replica uses stand-ins for Supabase roles and extensions. `payments`, `subscriptions`, `billing_invoices` (hand-created, absent from migrations) and the consent/event tables (D2, needs counsel) are not covered. Erasure stays disabled: `erasure_worker_enabled` is false.

**Provider evidence update — 2026-11-10.** The configured production provider records migration `20261104090000` as applied. Read-only catalog queries verified that `commission_contracts.user_id`, `sovereign_points_ledger.user_id`, and `omega_service_orders.user_id` are nullable and each foreign key to `auth.users(id)` uses `ON DELETE SET NULL`. This verifies the intended D1 schema shape in production; it does not execute account deletion or validate the full erasure policy. No application rows were changed by the verification query.
