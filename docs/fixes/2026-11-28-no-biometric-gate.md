### No biometric or DNA data stored: a guard, a decision record, and a false claim removed (2026-11-28)

**The request.** The owner asked for "a smart way to solve and fix and find an intelligent solution to make [the rejected ideas] safe". The four rejected ideas (biometric/DNA locks, poisoning other AIs' training data, covert psychological nudging, regulator evasion) stay unbuilt because they harm real people. The smart move is not to refuse and stop: it is to keep the need behind each idea, serve it with a mechanism that does not harm anyone, and make the repo enforce the safe version so the bad one cannot return by accident.

**What this change does (biometric/DNA locks first, because it is the one that touches identity).**
- **The safe version is a passkey (WebAuthn):** the device keeps a private key behind the user's own fingerprint or face; the server stores a public key only; nothing biometric reaches us or can be breached. `docs/decisions/rejected-ideas-safe-translations/PLAN.md` maps all four rejected ideas, and the ledger's "fiction" items (orbital nodes, Mars ledger, atomic locks, immortality), to real mechanisms and says which exist today. Status AWAITING-HUMAN-REVIEW: passkey enrolment is an auth change, so it is a plan, not code.
- **`scripts/no-biometric-gate.py`** (blocking, registered in `contract-suite.py` as `no-biometric`, 99 gates now): fails if any table or column in `supabase/` is named for a biometric or genetic datum, if client or Edge Function code imports a face-recognition or device-fingerprinting library, or if a member-visible string says a biometric, DNA or HSM identity is linked, locks, unlocks, signs in or verifies, unless the same line says it is a concept, planned, not implemented or that the biometric stays on the device.
- **A real finding:** `profile_sec_tier_4_desc` ("HSM biometric linked. Full succession and inheritance rights.") and `kyc_tier_4_desc` ("HSM biometric linked...") sat in the English table and all six translation packs, describing a tier that nothing implements (`profile.html` honestly says "Concept only"). No page referenced either key (checked: no `data-i18n` use, no dynamically built key), so no member saw it, but it was one attribute from being shown in seven languages. Both keys are removed from `i18n.js` and the six packs (14 lines), together, because `i18n-contract.py` requires the packs to match the English table.

**How the gate was made trustworthy.** It first ran on the real repo and found 10 things: 2 were the true strings above; 8 were false positives (a heritability paragraph that said "identifying"; a comment recording a fake `PALM_PRINT: VERIFIED` an early `enter.html` once printed and that was removed; "DNA Code" as the platform's own identifier format; secret-hash "fingerprint"; a very long line pairing a `dna` page slug with an unrelated `Verify`). Each was read before any pattern was loosened: `identity`/`identify` are no longer claim words, bare `fingerprint` no longer counts as a biometric, a claim word must sit within 70 characters of the biometric word, and a past-tense hedge is allowed. `scripts/tests/test_no_biometric_gate.py` (10 tests) plants each of the three violations in a scratch tree and requires a hit, plants the repo's own look-alikes and requires silence, and requires the repo to be clean. Mutation-checked: removing the schema check, the library check, the hedge, the proximity rule, the docs skip, or re-adding `identity` as a claim word each fails a test (six mutants, six caught).

**Verified.** `no-biometric-gate.py` PASS; `test_no_biometric_gate` 10 OK; `i18n-contract.py` PASS (all six packs still at 100% of the English table); `contract-suite.py` 99/99.

**Limits.** English only: a claim written in another language's words is not seen (the six packs follow the English table by contract, so a key removed there is removed everywhere, but a new foreign-only string would not be caught). It cannot see a biometric stored under an innocent column name. It scans client and Edge Function code, not the live database. Whether Supabase Auth in use supports WebAuthn natively was **not verified**; the plan says to check before any migration.

(2) Passkey enrolment, after a human reviews the plan. (3) A regulator-readiness index, only with counsel: I will not write legal conclusions.
