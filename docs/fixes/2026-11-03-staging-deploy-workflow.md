### Supabase staging deploy workflow (written, not yet run) (2026-11-03)

**Why.** Merging to `main` deploys migrations and functions to production within about a minute (CLAUDE.md §8.2), and the only existing push workflow, `supabase-controlled-migration-push.yml`, targets production and applies one pre-approved migration. There was no place to run the 413-file migration history against a real Postgres first. The owner supplied a second Supabase project (`nvgedlxlkdzvcelimbvq`); this session's connector could not see it (`list_projects` returned three projects in another org; `get_project` returned "You do not have permission"), so it could not be set up directly.

**Fix.** Added `.github/workflows/supabase-staging-deploy.yml` (manual only) and `docs/STAGING_ENVIRONMENT.md`. The workflow takes the project ref from `vars.STAGING_PROJECT_REF`, refuses the production ref, uses separate `STAGING_*` secrets, dry-runs, applies, and requires every remote version to match a local file; it can optionally deploy the Edge Functions.

**Verified.** `workflow-contract.py` and `workflow-contract-lint.py` pass; the file parses as YAML. The refusal block was run locally against six inputs: production ref, no confirmation, unset ref, short ref, missing token each refused, and the valid staging ref allowed. The post-push history check was run against sample `supabase migration list` output built from the 413 real local versions: matching rows give 0 mismatches, and one blank Remote gives 1 (caught).

**Not done / not verified.** The workflow has **never run**: no staging token or database password exists in the repo's secrets, so `supabase link`, `db push` and `functions deploy --use-api` are unexercised, and whether all 413 migrations apply cleanly to an empty Supabase project is unproven (CI's "Fresh database replay" proves a local Postgres, not Supabase's). The CLI's table format was assumed from the production workflow, not observed. No frontend uses staging. Edge Function secrets, Auth settings and data are not set up. **Found, not fixed:** `scripts/migration-history-contract.py:82` counts a blank-Remote row as applied remotely, so `--remote-output` can never report a version missing remotely; a sample with one remote version removed still printed "exactly synchronized".
