### Two real bugs found while testing the canvases, fixed: wallet's deleted chart, and agent-network's runaway canvas (2026-11-24)

Both were recorded as OPEN in `GAP_ANALYSIS.md` §S by the hi-DPI work (found while testing, out of its scope) and are closed here.

**1. `wallet.html` threw `ReferenceError: drawAllocCanvas is not defined` on load.**
*Cause.* Commit `eb32eeb85` ("show no wallet balance before an account is recorded") rewrote `renderOverview` and, in the same diff, deleted `renderAllocBars` and `drawAllocCanvas` while keeping the calls to them (CLAUDE.md §8.1 class 4). The allocation chart and bars never drew, for anyone, and nothing noticed. *Fix.* Both functions restored from that commit's parent. They read only `accounts` (no invented figures), so restoring them keeps the commit's intent: an empty wallet shows no balance, the chart reads "NO ACCOUNTS", and there are no bars. Two deliberate changes: the bars are built with `textContent` rather than `innerHTML` (account types come from locally stored data), and the chart draws through `omega-canvas-hidpi.js`.
*Evidence, same harness, before and after.* `origin/main`: an empty and a seeded wallet both log the error, draw nothing (0 painted pixels, 0 bars). Branch: neither errors; empty shows `—` and the "NO ACCOUNTS" line; seeded shows `$26,000`, the chart (13 percent of pixels) and 4 bars; at 3x the store is 2742x600, three times the 914x200 it draws at 1x. `scripts/tests/test_wallet_alloc.py` fails when either function is removed again (mutation-checked).
*Not fixed.* The chart measures `offsetWidth` before the layout settles (914 px into a 778 px box): the original function did the same.

**2. `agent-network.html`'s canvas grew without bound.**
*Measured on `origin/main`* (headless Chromium, 1000x1500, 1x): 1,066, 1,495, 1,924, 2,275 ... 3,679 px over 12 s with motion, 1,300 ... 4,615 with reduced motion, and 5,044 to 5,200 px during a single pointer scan. *Cause (confirmed by the fix, not only reasoned).* `#network-canvas` was `width:100%; height:100%` of `.network-container`, whose height is the status line plus the canvas; `drawNetwork()` stored `canvas.offsetHeight` as the canvas height and a `ResizeObserver` re-ran it, so each pass grew the container by the status line and the canvas followed. *Fix.* The canvas is absolutely positioned (`inset:0`) in the container, which gets `min-height:60vh`; the status line sits above it (`z-index:2`). *Result:* 900 px, unchanged across 8 samples over 12 s, in both motion modes.
*What changed visibly:* the canvas is a stable 60 percent of the viewport height. It was meant to fill the page, but the page's flex layout never gave the container more than that, so this is not a regression from "fill".
*Verified.* The pointer harness gained a check that the canvas box does not change size while the page is scanned; it **fails on pristine main** (5,044 to 5,200 px) and passes on the branch (11/11), and the chart harness passes (6/6). The harnesses used to freeze this page's height (`#network-canvas{height:520px!important}`) to work around the growth; that workaround is removed, so they now test the real page. `test_the_canvas_does_not_size_its_own_container` fails if the canvas goes back in the flow.
*Side effect on an earlier claim.* The hi-DPI helper rule "never pin a height" could not be caught by any browser test while this page was frozen; unfrozen, it still cannot, because the cyclic percent-height that triggered the old bug no longer exists. The static contract remains the guard (docstring corrected).

**Not done / not verified.** (1) Headless Chromium only; not a real browser or device, and not production. (2) `agent-network`'s agents were not exercised beyond the pointer harness's synthetic and real clicks. (3) **Is wallet's bug repeated elsewhere?** `node scripts/verify-runtime.js --all` over all 242 pages (headless, stubbed Supabase) found **no page that throws on load**: 237 ok. The 8 failures are all text contrast (dark red on near-black, 1.8-1.95:1), an unrelated pre-existing item now in `GAP_ANALYSIS.md`. A page that throws only after an interaction is not covered by that sweep.
