### PR conflicts: removed the shared lines, not just resolved them (2026-11-02)

**Why.** #1135 went from `clean` to `dirty` within an hour because #1133 merged first, and earlier the same day #1133 and #1130 had needed the same hand fix. Measured on the last 12 merges: `FIXES_LOG.md` was touched by **12 of 12**, `CLAUDE.md` by 7 (count lines), the XSS/CSP baselines by 3 to 4 each, `nav.js` by 4, generated page-contract files by 3. Every PR appended its entry to the same end-of-file position, so any two open PRs conflicted by construction.

**A rule that looked right and is not.** `FIXES_LOG.md merge=union` in `.gitattributes` keeps both sides of an append when *git* merges. Tested on real PRs against a throwaway base branch (two PRs each appending a line at the end; A merged; B then reported): **`mergeable_state: dirty`**. GitHub does not honour it, so it would only have saved a manual resolution, never the "conflicting" flag. Not shipped.

**What shipped instead.** (1) Each fix entry is its own new file, `docs/fixes/<date>-<slug>.md`, created by `scripts/new-fix-entry.py`; two PRs cannot touch the same line. (2) `FIXES_LOG.md` is frozen history; `scripts/fixes-log-frozen.py` (gate `fixes-log-frozen`) fails if it changes, with the instruction to move the entry, so the old habit cannot silently return. (3) The same gate fails if `CLAUDE.md` states a per-PR count (`**N** tests`, `**N** blocking checks`, `holds **N** gates`): the gate found one I had missed (`**23** tests`, line 562) the first time it ran. Those four counts were removed. (4) `scripts/merge-main.py` merges `origin/main` (a merge commit, never a rebase) and resolves the classes that are always resolved the same way: `FIXES_LOG.md` keeps both sides; the three ratchet baselines take the lower value per key; `OMEGA_SKILL_REGISTRY.md` and the page-contract JSON take main's and regenerate. A conflict in anything else is left in place and listed.

**Verified.** 17 tests in `test_conflict_proofing.py`, the helper run against real temporary git repositories: two appends to `FIXES_LOG.md` both kept in order with one merge commit and a clean tree; baselines lowered per key; a key migrated to zero on either side dropped; a real logic conflict (`x=2` vs `x=3`) left conflicted with exit 1; a clean merge; a dirty tree refused untouched. The gate fails on an append, on an edit to history, on a missing hash file, on a mis-named entry file, and on a per-PR count in `CLAUDE.md`, and passes on the real tree.

**Not done / not verified.** This removes the *structural* conflicts. Two PRs that edit the same lines of the same page (for example `nav.js`, which 4 of the last 12 merges changed) will still conflict, and `merge-main.py` will leave that for a human by design. The helper was tested on temporary repositories, not yet on a live conflict in this repo. The weekly-ideas automation reads `CLAUDE.md` at session start and should follow the new rule; until it does, its PR will fail `fixes-log-frozen` with the instruction, which is the intended correction. Three throwaway branches (`tmp/ct-a`, `tmp/ct-b`, `tmp/ct-base`) could not be deleted from here (`git push --delete` fails through this proxy) and need removing in the GitHub branches page; they never touched `main`.
