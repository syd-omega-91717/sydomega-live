## ◈ What Ω SYD OMEGA 91717 Is

**Ω SYD OMEGA 91717 is one platform expressed through many domains.**

The current engineering model is:

> **One governed core. Many domain projections. One coherent identity, policy, capability, task, data, event, evidence, truth, and release model.**

The product brings together concepts spanning:

- Identity and profile
- Knowledge, learning, and progression
- Intelligence, research, and AI-assisted workflows
- Creation, publishing, and media
- Family, heritage, and continuity
- Finance, investment, commerce, and marketplace experiences
- Blockchain and digital-asset experiences
- Communication and community
- Gaming and achievement systems
- Governance, security, audit, lineage, and evidence
- A world/graph layer connecting people, content, capabilities, tasks, and evidence

The intended experience is **one living ecosystem rather than a collection of disconnected dashboards**.

---

## Ω The Unified Core

Omega is deliberately not treated as hundreds of independent pages.

The platform's current operating model is **ONE_GOVERNED_CORE_MANY_DOMAIN_PROJECTIONS**.

| Shared authority | Purpose |
|---|---|
| Identity & policy | Authentication, authorization, roles, ownership boundaries |
| Page contracts | Defines the job, data, actions, states, and evidence expected from each page |
| Capability registry | Canonical capability declarations and governance |
| Task fabric | Request → authorization → execution → verification |
| Data & content fabric | Canonical data, provenance, rights, lifecycle, and access policy |
| Event & evidence fabric | Durable events, evidence, lineage, replay, and auditability |
| Truth vocabulary | Distinguishes live, calculated, simulated, lore, unavailable, blocked, and other states |
| Navigation & design | Shared information architecture and visual primitives |
| Release evidence | Gates that distinguish source implementation from runtime/production proof |

### Governing lifecycle

**SOURCE REQUIREMENT → DOMAIN → PAGE → CAPABILITY → TASK → AUTHORIZATION → EXECUTION → EVENT → EVIDENCE → TRUTH STATE → RELEASE STATE**

This is the core mechanism for preventing a visually complete feature from being mistaken for a production-complete feature.

## ◎ Intelligence & Governed Agents

The conceptual Omega agent layer includes:

**Sentinel · Analyst · Historian · Tutor · Merchant · Proxy · Oracle · Scout · Warden · Auditor · Beacon · Sovereign**

An agent role is not an authorization bypass.

AI-enabled capabilities are expected to:

1. Use authoritative data where available.
2. Preserve provenance and evidence.
3. Respect identity and authorization boundaries.
4. Distinguish generated/inferred output from verified facts.
5. Fail closed for sensitive operations.
6. Record evidence for important actions.
7. Avoid presenting client-side state as authoritative financial, ownership, security, or deployment truth.

---

## ◇ Truth Is a Product Feature

Omega intentionally does not treat every number, balance, achievement, status, visualization, or AI response as factual merely because a UI can display it.

The platform uses explicit truth and lifecycle states, including:

**LIVE · IMPLEMENTED · RUNTIME-VERIFIED · PRODUCTION-VERIFIED · PARTIAL · CALCULATED · SIMULATED · USER-CREATED · EMPTY · UNAVAILABLE · UNVERIFIED · BLOCKED · LORE · FUTURE · REJECTED · REPLACED**

For example:

- A simulated market scenario is valuable when it is clearly **SIMULATED**.
- A calculated progression score is useful when it is clearly **CALCULATED**.
- Provider-backed production behavior requires actual runtime evidence before it is labelled **PRODUCTION-VERIFIED**.

This distinction is an architectural control, not merely a visual convention.

---

## ▲ Evidence-First Engineering

Omega uses an explicit readiness ladder:

**SPECIFIED → IMPLEMENTED → CONNECTED → PERSISTED → SECURED → TESTED → DEPLOYED → LIVE-VERIFIED**

A source file, SQL migration, UI component, prompt, or local test does not by itself prove provider-side production behavior.

The engineering system therefore treats evidence as a first-class artifact across:

- Database and RLS security
- RPC privilege boundaries
- Storage and sensitive uploads
- Authentication and MFA-sensitive actions
- Payments and provider callbacks
- AI configuration and quality
- Privacy lifecycle
- Reliability and recovery
- Deployment and runtime parity
- Release governance
- Audit and lineage

**If evidence is missing, the system must say so.**

## 🧭 Page & Capability Governance

The page estate is being governed as a product surface rather than as an uncontrolled collection of HTML files.

For each governed page/capability, the engineering model asks:

1. What user problem does this solve?
2. Which domain owns it?
3. Which canonical capability does it invoke?
4. What authoritative data does it require?
5. Who may perform the action?
6. What happens when access is denied?
7. What is the truth state?
8. Which events and evidence are required?
9. How does it fail, retry, or recover?
10. How is it tested?
11. What proves provider/runtime behavior?
12. How is it rolled back or retired?
13. Who owns operational cost and residual risk?

Unknown controls are **remediation work**, not an excuse to create synthetic mappings.

## 🛠 Definition of Done

A feature is not production-complete merely because:

- a page renders;
- JavaScript exists;
- a migration exists;
- a prompt exists;
- a local/static test passes; or
- a UI control appears clickable.

Applicable production completion requires the relevant:

- contract
- authorization cases
- negative cases
- failure and retry behavior
- source traceability
- tests
- telemetry/evidence
- runtime verification
- deployment evidence
- documentation
- rollback or retirement path
- accountable owner

## 📚 Source Corpus & Evolution

The project's historical source corpus contains both **implemented-direction requirements** and **aspirational/experimental concepts**.

Some early source material describes architectures such as React/Vite, Express microservices, Redis, Docker, Kubernetes, or other infrastructure. Those documents are preserved as design history and requirements input; they are **not automatically treated as the current implementation architecture**.

The current repository architecture is authoritative for implementation decisions.

When a source concept is valuable, the project follows this rule:

1. Identify the underlying principle.
2. Separate fact from narrative or aspiration.
3. Compare it with the current architecture.
4. Adapt only what improves the governed core.
5. Define dependencies and migration impact.
6. Add tests and evidence.
7. Preserve rollback or retirement.
8. Never copy proprietary implementation.

This allows Omega to evolve without becoming architecturally inconsistent.
